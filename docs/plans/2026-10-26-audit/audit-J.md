## Dependency & Supply Chain Risk - Audit Results
**Score**: 3/4. The dependency tree is small, current, locked and uses pure-Rust TLS, and nothing found here can be exploited today. Two things keep it from 4/4. The first is process: the lock file has never been refreshed and nothing audits it, so all 67 releases shipped a yanked crate and an outdated root store. The second is resilience at the edges: network errors reach the user without their cause, and the self-updater has no timeout and no size cap.
**Files reviewed**: 24. In scope: `Cargo.toml`, `crates/killi/Cargo.toml`, `Cargo.lock`, `install.sh`, `update.rs`, `scripts/release.sh`, `releases/latest.toml`, `RELEASING.md` and `.github/workflows/ci.yml`. Integration code: `llm/mod.rs`, `tools/web.rs`, `login.rs`, `login/opencode_go.rs`, `login/chatgpt.rs`, `config.rs`, `snapshot.rs`, `mcp.rs`, `main.rs` and `tui/mod.rs`. Context: `docs/decisions.md`, `README.md`, `AGENTS.md` and both intel briefs. I also read the vendored sources of reqwest 0.12.28, tokio 1.54.0/1.54.1 and webpki-roots 1.0.10/1.0.11.

### P1 - High
- **[Cargo.lock:1551-1552, Cargo.lock:1879-1880, .github/workflows/ci.yml:29-30, scripts/release.sh:12-14]** The lock file has never been refreshed, and nothing checks it for advisories or yanks. As a result, every release ships tokio 1.54.0, which is yanked and carries RUSTSEC-2026-0384.
  Scenario: The first lock (31ad771) was written on 10-21 at 16:28 UTC. tokio 1.54.1 was published at 21:05 UTC the same day (crates.io API), and 1.54.0 is yanked. All 68 revisions of `Cargo.lock` in git have the same tokio/rustls/rustls-webpki versions (1.54.0 / 0.23.46 / 0.103.16), so `cargo update` has never run. CI and `release.sh` build with `--locked` and run neither an audit nor a yank check, and there is no Dependabot or Renovate config. The next advisory against reqwest, h2 or rustls will ship in the same way.
  Impact: Today the exposure is nil. The race needs the multi-threaded runtime, and `rt-multi-thread` is not in killi's unified tokio features (`cargo tree -e features -i tokio`). All four `Interval` users (tui/mod.rs:411, update.rs:81, update.rs:155, broker.rs:218) run on `new_current_thread()` (main.rs:65). The 1.54.0→1.54.1 diff only reverts tokio#8458 in the time driver. The process gap is the real problem: the same gap also left webpki-roots outdated (see P2), and `cargo audit -D warnings` currently fails, so an audit gate can't be added until the lock is fixed.
  Verified: tested. Re-ran `cargo-audit audit --db … -D warnings` with a fresh database (1,355 advisories): 1 vulnerability and 1 yanked crate. The 3 new advisories since intel-0b's run are pingora advisories and don't apply. In a scratch copy, `cargo update` changes 15 packages, all MSRV-1.94-compatible. After it, `cargo clippy --workspace --all-targets --locked -- -D warnings` passes, `cargo test --workspace --locked` passes 338 of 338, the audit exits 0, and the stripped release binary changes by 16 bytes. `cargo update -p tokio` alone also passes but re-points a few lock-only `windows-sys`/`syn` edges; those crates aren't compiled on macOS.
  Suggested fix: Run `cargo update` (all 15 packages; this also brings webpki-roots 1.0.11), not just `-p tokio --precise 1.54.1`. Add `cargo audit -D warnings` (or `cargo deny check advisories`) to `release.sh` before the build, since that script is the real release gate (CI doesn't gate releases, intel-0b). Add the same as a CI step, plus `.github/dependabot.yml` with `package-ecosystem: cargo`, weekly.

- **[llm/mod.rs:184, llm/mod.rs:212; login/chatgpt.rs:185, login/chatgpt.rs:187; tools/web.rs:496, :498, :524, :526]** Transport errors are formatted with reqwest's `Display`, which never prints the cause. A DNS failure, a refused connection, a TLS rejection and a timeout all read the same, and each is retried for minutes before the user sees anything.
  Scenario: The VPN is off for the user's gateway, the base_url has a typo, the user is offline, or a corporate inspection CA or expired certificate makes rustls reject the server. In each case `request.send()` fails, the code builds `Failure::transient(format!("request failed: {e}"))`, and the client retries 10 times. Each retry draws a row like `⚠ retry n in 0:0x: request failed: error sending request for url (https://…/v1/chat/completions)` (tui/mod.rs:1862). Then the turn ends with the same text plus "(after 10 attempt(s))". That takes about 2.1–2.7 minutes for DNS, refused or TLS errors and about 7 minutes for a host that drops packets (10 × 30 s connect timeout plus backoff). `stream interrupted: {e}` (:212) hides mid-stream timeouts and resets in the same way. The ChatGPT token refresh (`error.to_string()`) and web_search errors, which the model reads, hide them too.
  Impact: This is the integration failure a user is most likely to hit, and the error text is all they get. They can't tell "connect the VPN" from "the provider is down" from "your network intercepts TLS", and retrying a certificate failure can't help.
  Verified: tested. A probe in `scratchpad/J/ws-pdf` (llm/mod.rs, `transport_error_probe`) used killi's client settings. It printed the same shown text, `error sending request for url (…)`, for all three cases. The hidden causes were `received corrupt message of type InvalidContentType` (TLS), `tcp connect error <- Connection refused (os error 61)` and `dns error <- failed to lookup address information`. reqwest 0.12.28 `error.rs:227-267` never writes the source.
  Suggested fix: `tools/web.rs:103-123 fetch_error` already walks `source()` and adds hints. Move it to a shared helper and use it at these sites, with the innermost cause first, because the retry row is `Line::Fit` and gets cut at the right edge (tui/mod.rs:3224). For example: `could not reach api.x.com: dns error: failed to lookup address`. Classify certificate failures (`invalid peer certificate`, `UnknownIssuer`, `Expired`) as fatal so they fail on the first attempt with that hint.

### P2 - Medium
- **[crates/killi/src/update.rs:42, :65, :75-95, :97-106; install.sh:13-14]** `killi update` has no connect, read or total timeout, and no size cap. It also installs whatever matches the checksum without checking that the new binary runs. `install.sh`'s curl has no timeouts either. This confirms part of lead 0a-15.
  Scenario: A stalled proxy, Wi-Fi that drops mid-download, or a hostile mirror (`KILLI_RELEASES_URL` is accepted over http) leaves the update hanging forever, with the status line still animating, or lets it eat memory until macOS kills it. The update runs often: there were 67 releases in 4.75 days.
  Impact: The CLI hangs until the user presses Ctrl-C (Ctrl-C does exit cleanly). Memory use is unbounded. A broken release (wrong architecture, crash at startup) replaces a working binary, and no rollback is kept.
  Verified: tested with `scratchpad/J/scripts/fake_releases.py`, `drive_update.py` and `drive_big.py` against the release build. With headers that never arrive, the update was still running at 40 s. With 1 KB of a 7 MB body and then silence, it was still running at 40 s. With an endless chunked body throttled to about 45 MB/s, RSS grew in a straight line: 3 → 45 → 82 → … → 407 MB in 11 s. In `ok` mode, killi installed a 32-byte shell script as `killi` (inode changed, staging file removed).
  Suggested fix: Build the client like `login.rs:98-101` (connect 30 s), add `read_timeout(60 s)`, refuse a `Content-Length` over 64 MB, and stop reading at 64 MB. Hash in memory with `ring::digest::SHA256`, which is already linked (chatgpt.rs:563), instead of shelling out to `/usr/bin/shasum` and ignoring its exit status (:98). That also removes the confusing "expected , downloaded …" message. Before the `rename`, run `<staging> --version` and require `killi <version>`. In `install.sh`, add `--connect-timeout 30 --max-time 600` to curl.

- **[Cargo.lock:1879-1880 (webpki-roots 1.0.10); Cargo.toml:19 (`rustls-tls` = compiled-in roots)]** The shipped root store still trusts two eMudhra roots that webpki-roots 1.0.11 removed on 10-23.
  Scenario: webpki-roots 1.0.10 cleared RUSTSEC-2026-0381 (emSign ECC Root CA - G3). On 10-23, 1.0.11 removed "emSign Root CA - C1" and "emSign ECC Root CA - C3" after the CCADB removal (Mozilla bug 2083709, release notes for rustls/webpki-roots v/1.0.11). killi compiles the roots in and never checks for updates by itself (intel-0b), so every installed copy trusts these two roots until it is rebuilt and the user runs `killi update`.
  Impact: The risk is low. An attacker would need a certificate chaining to those CAs plus a network position. The prize is high, though: provider API keys and prompts travel over these connections.
  Verified: traced. I diffed the vendored sources (1.0.10 has 120 roots, 1.0.11 has 118, and the two missing are emSign C1 and C3) and read `gh release view v/1.0.11 -R rustls/webpki-roots`.
  Suggested fix: Run the same `cargo update` as in the first P1. Longer term, consider OS trust: reqwest 0.13's `rustls` feature uses rustls-platform-verifier, and on 0.12 `use_preconfigured_tls` can take a platform-verifier config. Distrust would then arrive with macOS updates, and Keychain CAs (corporate gateways) would work. Measure size and startup first.

- **[login/opencode_go.rs:131-141; config.rs:305-312]** Lead 0a-14 is confirmed. Each OpenCode Go model's `base_url` is copied from models.dev's `provider.api` without checking its host, and the provider's key is sent there.
  Scenario: At `killi login opencode-go`, `go_models` writes a model `base_url` whenever the catalog's `api` differs from Go's own URL. At request time, `resolve` prefers the model's `base_url` and pairs it with `provider.key()`. A poisoned or compromised catalog entry (models.dev is an open, community-PR repository) would therefore be written into `~/.killi/config.toml`, and from then on every request on that model would send `Authorization: Bearer <OpenCode key>` plus the full conversation to that host.
  Impact: The key and the user's code would be exfiltrated persistently and silently. Likelihood is low.
  Verified: traced. I also checked the live data: of the 37 `opencode-go` entries in today's catalog (`api.json`, 5.9 MB, parsed with `python3 -I`), all 37 point under `https://opencode.ai/inference/go/`, so a prefix check would drop none.
  Suggested fix: In `go_models`, skip and name any model whose `api` doesn't start with `https://opencode.ai/inference/go/`, the prefix `ours()` already uses (opencode_go.rs:27).

- **[tools/web.rs:139]** `pdftotext` runs with no timeout, no `kill_on_drop` and no `own_session`. A hung run holds `fetch_url` and survives Esc, which breaks decision 39's "every child gets its own session".
  Scenario: A pathological or very large PDF (up to the 10 MB cap) makes poppler spin. The tool call waits forever. When Esc drops the future, the child keeps running, and `tools::kill_all` on a signal doesn't reach it.
  Impact: The turn is stuck until Esc, and a CPU-burning orphan outlives killi.
  Verified: tested. `cargo test -p killi pdf_orphan_probe -- --nocapture` in `scratchpad/J/ws-pdf` put a fake `pdftotext` first on PATH and served a local `application/pdf`. `fetch_url` hung for 5 s. After the future was dropped, `pgrep` still listed `/bin/sh …/pdftotext -layout …/killi-pdf-<pid>-….pdf -`, while the temp PDF itself was already gone.
  Suggested fix: Copy `browser()` (web.rs:222-243): `.own_session().kill_on_drop(true)`, and wrap `.output()` in `tokio::time::timeout` (for example `BROWSER_TIMEOUT`) with a "pdftotext took too long" error.

### P3 - Low / Nits
- **[update.rs:62-72, :52, :53; install.sh:13-16]** Lead 0a-15 is confirmed. The checksum and the binary come from the same repository, branch and path, so the check gives integrity, not authenticity. A stolen GitHub token or session can push both files.
  Hardening cost against value: verification is essentially free. `ring::signature::ED25519` is already linked, or `/usr/bin/ssh-keygen -Y verify` works with no new dependency. Either takes about 30 lines plus a signing step in `release.sh`, with `install.sh` trusting the key on first use. The cost is custody of the key across the user's 2–3 Macs, and the value is only against a compromise on GitHub's side, which 2FA mostly covers. My recommendation is "not now". Do it before promoting `curl | sh` to other people.
  Smaller points: there is no `sync_all` before the `rename` (:53; chatgpt.rs:78-86 has the pattern). An `http://` `KILLI_RELEASES_URL` is accepted (my tests ran over plain http). Rebuilding the same commit with the same 1.97.1 toolchain at a different path gives a binary 82 KB larger (embedded paths; `release.sh` remaps only `$HOME`), so a published binary can't be checked against its source by rebuilding.
  Verified: traced, and partly tested.

- **[.github/workflows/ci.yml:24-28; Cargo.toml:9]** Three compilers are in play, and the MSRV is tested nowhere. CI used rustc 1.99.1 (log of run 40310651195: "stable … updated - rustc 1.99.1"). Releases build on 1.97.1. `rust-version = "1.94"` was built once, by intel-0b. A new stable's clippy lints under `-D warnings` can turn CI red with no code change. The action refs are mutable tags (`checkout@v7`, `rust-cache@v2`, `rust-toolchain@stable`).
  Verified: traced from the CI log and `rustc --version`.
  Suggested fix: Add a `rust-toolchain.toml` with `channel = "1.97.1"` and `components = ["clippy"]`, so CI uses what the release machine uses and bumps are deliberate. Either add an MSRV job (`dtolnay/rust-toolchain@1.94` plus `cargo check --workspace --all-targets --locked`; intel-0b measured about 26 s) or raise `rust-version` to what is tested. Pin the actions to commit SHAs.

- **[releases/killi-arm64; RELEASING.md:3-5]** Committed binaries make the repository grow, and a commit-pinned rollback is possible but undocumented. There are 67 binary blobs, 447 MB raw and 135 MB on disk (about 2.0 MB per blob compressed). A fresh `git clone --bare --no-local` pack is 70 MiB, of which about 1 MiB per release is the binary after deltas. So intel-0b's "about 7 MB per release" overstates the growth. At about 14 releases a day that is still about 15 MiB a day, and every full clone pays it. CI does a shallow checkout and users fetch the raw file, so neither is affected. Raw files also lag about 5 minutes after a push (RELEASING.md), which makes `killi update` fail with "checksum mismatch" right after a release, without saying why.
  Verified: tested (`git cat-file --batch-check` over `releases/killi-arm64`, local bare clone).
  Suggested fix: Publish to GitHub Releases (`gh release create`) and point `install.sh` and `update.rs` at `/releases/latest/download/{killi-arm64,latest.toml}`, keeping one bridge release on the raw path for old clients. For rollback today, `curl -fsSL …/install.sh | KILLI_RELEASES_URL=https://github.com/timwuhaotian/killi/raw/<commit>/releases sh` works: I verified it on 0.4.19's `latest.toml`, and the binary URL redirects (302) to raw. `update.rs:45` refuses downgrades. Document the install.sh route or add `killi update <version>`.

### Checked and fine (one line each: what you looked at that holds up — saves the next reader time)
- RUSTSEC-2026-0384 can't happen here: tokio has no `rt-multi-thread` feature, every `Interval` runs on the current-thread runtime, and 1.54.1 is a revert confined to `runtime/time` and `time/{interval,sleep}.rs`.
- TLS crates sit exactly at the patched minimums: rustls 0.23.46 (RUSTSEC-2026-0346 to -0349), rustls-webpki 0.103.16 (-0382), webpki-roots 1.0.10 (-0381), h2 0.4.20 (-0258). tokio also meets -0386 (≥1.53.3). No newer compatible rustls or webpki exists.
- `cargo update --dry-run` moves 15 packages and holds back base64 0.23 and reqwest 0.13. reqwest 0.13 is not a drop-in: `rustls-tls` is gone, `query`/`form` become opt-in, and it needs base64 ^0.23. Defer it. Caret ranges plus `--locked` everywhere are fine.
- Binary-size A/B (stripped release, same flags; baseline 7,339,376 B): without dom_smoothie, 6,203,040 B (−1.14 MB, −15.5%). That is an upper bound, because the variant swapped readability for `plain()`, which keeps `<script>`/`<style>` text. Keep it (decisions 12 and 19). cargo-bloat attributes about 400 KiB of `.text` to dom_smoothie, html5ever, dom_query and selectors; the rest is data tables.
- `http2` costs −0.50 MB (−6.8%, 6,837,088 B). Keep it: decision 18 names it, ALPN negotiates it with providers that offer it, and subagents and swarm members share one `Client`, so h2 multiplexes up to 128 concurrent requests instead of opening 128 TLS connections.
- `regex` is needed: the `grep` tool compiles user patterns (search.rs:295) and hook matchers use it (hooks.rs:100). regex-automata, regex-syntax and aho-corasick come with globset and ignore anyway, and `regex` itself is 7.9 KiB. Per-call `Regex::new` belongs to C (0a #16).
- cargo-bloat `.text` (4.8 MiB): killi 990 KiB, std 987, rustls 295, regex_automata 258, h2 204, tokio 154, regex_syntax 146, ring 139. The full table is in `scratchpad/J/bloat-crates.txt`.
- The duplicate base64 0.22.1/0.23.1 can't be fixed until reqwest 0.13. The duplicate `syn` 2/3 is build-time only.
- ring is rustls's provider and is used for PKCE (chatgpt.rs:552, :563), so it costs nothing extra. Its RUSTSEC-2025-0007 was withdrawn.
- Maintenance: dom_smoothie 0.18.2 (2026-09-21), dom_query 0.29 (10-23), html5ever 0.40.1 (09-14), unicode-width 0.2.2. crossterm 0.29.0 has been quiet since 2025-04-05 but has 53M recent downloads. Watch it; no action needed.
- reqwest defaults (TCP keepalive 15 s × 3) detect dead pooled connections after sleep. The LLM `read_timeout(300 s)` also bounds time-to-headers (reqwest client.rs:2637-2654, 3053-3058), so intel-0b's worst case of about 52 minutes for a stalled provider is right.
- `install.sh` verifies before `chmod`/`mv`/running, rejects an empty sha, uses `curl -f` with a cleanup trap, and its `mv` is atomic on one APFS volume. Truncation risk is low, since the script has no destructive commands.
- `update.rs` (tested): a new inode on rename, no staging file left behind, downgrade refused ("killi 0.4.20 is up to date" against 0.4.19), and an empty `sha256` fails closed because `shasum` printed a hash. intel-0b's residual case needs `shasum` to print nothing, which makes it a note, not a finding. Ctrl-C ends it cleanly. A partial download is safe: a stream that ends with an error writes no staging file, because `fs::write` runs only after the whole body arrives (update.rs:52-53), and a body that ends early but cleanly fails the checksum.
- Headless Chrome: 45 s timeout, `own_session`, `kill_on_drop`, `killpg` and profile removal on drop.
- PATH lookups (0b lead 15): `git` and `pdftotext` must come from PATH (Homebrew or the Command Line Tools). `osascript`, `sips`, `shasum`, `bash` and `sh` are absolute. `pbcopy` and `open` via PATH are harmless.
- Notarization and quarantine are accepted in decision 27, so I didn't re-report them.
- Integration failure modes, ranked by likelihood:
  1. Provider unreachable: the transport-errors P1.
  2. Provider stalls after accepting the connection: up to 300 s per attempt and about 52 minutes in all. Esc works in the TUI; `-p` responds only to signals (F).
  3. Synchronous `git add -A`/`write-tree` and `refresh_branch` block the UI for seconds on big trees (C).
  4. `killi update` stalls: the first P2.
  5. `pdftotext` hangs: the last P2.
  6. Headless Chrome is bounded.
  7. models.dev is read whole (5.9 MB) under a 60 s total timeout. That's fine.
