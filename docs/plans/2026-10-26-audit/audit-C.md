## Performance - Audit Results
**Score**: 2/4  (the hot paths are lean: a streamed delta costs ~27 µs and a request's conversion ~1 ms on real logs; but four synchronous stalls sit on the one runtime thread, one start-up path can leave an unkillable 100 % CPU process, and /undo rewrites the whole tree)
**Files reviewed**: 27 (main.rs, setup.rs, agent.rs, session.rs, snapshot.rs, live.rs, mcp.rs, broker.rs, prompt.rs, skills.rs, llm/{mod,openai,anthropic,responses}.rs, tools/{mod,files,bash}.rs, tui/{mod,history,text,editor,menu,mention,paste}.rs, plus crossterm 0.29 `terminal/sys/unix.rs`, `cursor/sys/unix.rs`, `event/source/unix/mio.rs`)
**Issues found**: 16 (P0 0 · P1 2 · P2 5 · P3 9)

**How it was measured.** Release build of 0.4.20 (`target/release/killi`, SHA-256 = `releases/killi-arm64`), copied to `scratchpad/C/killi-rel`. Pty probes with a scratch HOME and a scripted SSE server (`scratchpad/C/tools/{ptykit,fakesrv,hangup,hangup2,streamcpu,menucpu,startup}.py`); git probes on synthetic repos (`tools/gitbench.py`, `tools/undobench*.py`); in-process benchmarks added as `#[ignore]` tests to a scratch copy of the crate (`scratchpad/C/crate`, run with `cargo test --release -- --ignored --nocapture bench_`), with a counting global allocator for peak heap. The repository was not touched.
**Caveat on absolute numbers.** This Mac runs CrowdStrike Falcon, CyberArk EPM and Netskope, and other audit agents were building in parallel (load average 109 during the first git run, 4–9 for the numbers quoted). Here `/usr/bin/true` costs 7–9 ms to spawn and any `git` (the `/usr/bin/git` xcrun shim) ~30 ms. The durable findings are the *counts* (spawns per turn, walks per keystroke, copies per request); the milliseconds are this machine's, which is the user's real machine.

### P1 - High
- **[tui/mod.rs:3839, tui/mod.rs:1015; crossterm-0.29.0 src/event/source/unix/mio.rs:95-120, src/terminal/sys/unix.rs:243-265, src/cursor/sys/unix.rs:38-55; main.rs:121-139]** If the terminal goes away during start-up, killi spins at 100 % CPU forever and ignores SIGTERM and SIGHUP; only `kill -9` ends it.
  Scenario: `TerminalGuard::enter` calls `terminal::supports_keyboard_enhancement()` and `locate()` calls `crossterm::cursor::position()`. Both are crossterm's synchronous queries: write `CSI ?u CSI c` / `CSI 6n`, then loop on `poll_internal`. In `UnixInternalEventSource::try_read` the tty read loop never breaks on `Ok(0)` (EOF) or on an error other than WouldBlock/Interrupted, and the outer query loops treat `Err(_)` as "try again", so once the pty's master is closed (window/tab closed, SSH dropped, a pty harness exiting) the runtime thread reads EOF forever. killi caught SIGHUP/SIGTERM/SIGINT with tokio (`quit_on_signals`), so the kernel's SIGHUP no longer kills it, and the tokio task that would `exit()` never runs because the only runtime thread is inside crossterm.
  Impact: a core pinned until reboot or `kill -9`. **It is happening on this machine now:** pid 85171 (`target/debug/killi`, ppid 1, started Fri 23 Oct 14:00, state `Rs+`, 4,620 CPU-minutes ≈ 77 CPU-hours at audit time). `sample` shows 797 of 845 stacks in `read()` under `TerminalGuard::enter → supports_keyboard_enhancement → query_keyboard_enhancement_flags_raw → poll_internal → try_read` (`scratchpad/C/spin-sample.txt`). The project's own workflow (frames.py, screenshot.py, live_check.py, eval harnesses — AGENTS.md asks for frames.py after every TUI change) closes ptys; the memory note "process can be left orphaned … needs kill -9" is this bug. Same mechanism as intel-0a obs 8 (B) and the signal-path gap in obs 18 (K).
  Verified: reproduced (`python3 scratchpad/C/tools/hangup.py`, `hangup2.py`): A) master closed while killi waits for the `?u`/DA1 answer → alive, `Rs+ 100.0 %`, 3.02 s CPU in 3 s, alive after SIGTERM and after SIGHUP; A2) closed while `locate()` waits for the CPR → alive, 99.6 %, 3.01 s CPU in 3 s, alive after SIGTERM. Control runs: closed idle at the prompt (B) or mid-stream (C) → killi exits, since the signal task gets to run.
  Suggested fix: drop both crossterm sync queries and send `\x1b[?u\x1b[c` and `\x1b[6n` through a bounded-read helper built from the poll loop `query_ground` already has (tui/mod.rs:293-337: one write, one deadline, `read()==0` or an error means the terminal is gone → return/exit). It must run even when `[ui] theme` skips the colour query (tui/mod.rs:128), and it must keep reading until every expected answer has arrived or the deadline passes rather than stop at the first, since Kil answers DA1 before the OSC colours (the comment at tui/mod.rs:283-291) and an answer read late would be typed into the prompt. That also removes two sequential tty round trips (each up to 2 s on a terminal that doesn't answer) from start-up. Belt and braces (K's call): handle SIGTERM/SIGHUP on a plain thread (the SIGTSTP pipe+thread in `suspend_cleanly`, tui/mod.rs:3892-3925, is the pattern) so cleanup and `exit` don't depend on the runtime thread being free.
  Note for the user: `kill -9 85171` stops the orphan.

- **[snapshot.rs:115-119]** `/undo` rewrites every tracked file in the tree, not just the ones the turn changed.
  Scenario: `undo` runs `git read-tree <tree>`, which replaces the shadow index with entries that carry no stat data, then `git checkout-index -a -f`, which therefore sees every entry as changed and rewrites it. A turn that edited 1 file in a 2,001-file tree: undo took 1,556 ms (synchronously on the runtime thread) and changed the mtime of all 2,001 files.
  Impact: every undo looks like a whole-tree change to cargo/tsc/webpack/Vite watchers and IDEs: full rebuilds, re-indexing, "file changed on disk" for every open buffer; time and churn grow with the tree (a 20k-file tree is ~10× the writes).
  Verified: tested. `python3 scratchpad/C/tools/undobench.py <C> 2000`: "1 of 2001 files changed … 2001 files rewritten (mtime changed)". A scratch test added to the crate copy, `snapshot::tests::undo_rewrites_only_what_changed` (50 files, one edited, asserts no unchanged file's mtime moves), fails on the current code ("49 of 49 rewritten") and passes with the fix below; the two existing snapshot tests (restore changed/deleted, remove new, leave ignored; wait out another session's `index.lock`) pass with it too (`cargo test --release snapshot::` in `scratchpad/C/crate`, 3 passed). With the fix the 2,001-file undo rewrote 1 file, removed the file the turn had added, and took 593 ms (`tools/undobench2.py`).
  Suggested fix: in `Snapshots::undo` replace `read-tree <tree>` + the `ls-files --others` deletion loop + `checkout-index -a -f` with `read-tree --reset -u <tree>` (the index `write_tree()` just refreshed is stat-valid, so the two-way reset touches only paths that differ, and deletes paths added since the snapshot). Ignored files stay untouched as today.

### P2 - Medium
- **[tui/mod.rs:632; snapshot.rs:49-84]** The undo snapshot runs synchronously before every prompt's first request, with the UI frozen.
  Scenario: `prompt_turn` draws the prompt, then calls `snapshots.take()`: two blocking `std::process::Command` git runs (`add -A .`, `write-tree`), plus `std::thread::sleep(100 ms)` retries for up to 3 s when another session holds the shared `index.lock`. Only then does `agent.run` start. Measured on synthetic repos (load ≈ 9): warm take 203 ms (2k files), 235 ms (20k), 208–289 ms after 10 edits; the **first** take of a tree (every blob written as a loose object) 4.6 s (2k files) and 26 s (20k files) on this machine. By extrapolation a 49k-file tree (just under the 50k cut-off) would freeze the first prompt for about a minute here.
  Impact: every turn starts 0.2–0.3 s late with the spinner stuck on its first frame and Esc unread; the first prompt in a new project can hang for seconds to a minute; peers' `killi ask`/`tell` sockets go unanswered meanwhile.
  Verified: traced + tested (`python3 scratchpad/C/tools/gitbench.py <C> 2000 20000`).
  Suggested fix: run the git calls with `tokio::process::Command` and `tokio::time::sleep` (keeps keys and the spinner alive, no other change). The bigger win: start the snapshot concurrently with the first request and await it before the first tool call executes (requests take ≥3 s per decision 34, so the snapshot disappears from the critical path; a `UserPromptSubmit`/`SessionStart` hook that edits files would still need it first).

- **[tui/mod.rs:137 → snapshot.rs:33-47, 124-127; tui/mod.rs:1009 → 2513-2527]** Start-up does a tree walk of up to 50,001 entries and three git spawns before the first paint.
  Scenario: `Snapshots::new` walks the work tree (`too_many_files`, hidden files included) and runs `git --version`; `App::new` runs `refresh_branch` (2 more git spawns). Time from exec to the painted prompt (pty, terminal answering every query): 127 ms median in a 3-file repo, of which ~100 ms is the three git spawns here (`git --version` 33 ms, `rev-parse` 32 ms, `status` 36 ms, medians of 7); 569 ms in a folder of 60k files (walk ~440 ms, then undo is off anyway). The user does run killi in `~/code` (17 logs in that session folder; 62 repos, not itself a repo): the walk there took 704–1,212 ms in-process. For reference `killi --version` (the README's "starts in under 20 ms") is 9 ms.
  Impact: the interactive start is 6–60× the advertised figure; the 60k case pays half a second to a second to learn that undo is off.
  Verified: tested (`python3 scratchpad/C/tools/startup.py`; `BENCH_TREE=~/code cargo test … bench_too_many_files_walk`).
  Suggested fix: drop the `git --version` probe (a missing git already turns undo off at the first `take`, with its error); move the walk into `spawn_blocking` started at launch and awaited by the first `take` (or let the first `take` decide); run `refresh_branch` after the first `draw` (or asynchronously, see P3 below).

- **[tui/mod.rs:1375-1383 → mention.rs:14-31; tui/mod.rs:1202, 1160, 2745, 1455 → 1335-1346 → menu.rs:74-84, 123-160]** The `@` menu walks the tree synchronously and re-runs a 20,000-path fuzzy filter on every draw.
  Scenario: typing `@` runs `mention::list` (up to 20,000 entries, sorted) inside `draw()`; then `suggestions()` recomputes `menu::files` (lower-casing every path into a fresh `String` and `Vec<char>`) up to 3 times per key (`on_key_idle` :1202, `sync_menu` :1160, `live()` :2745) and once per draw while the agent works — every streamed delta and every 100 ms tick. In a folder of ~22k entries (pty, release build): `@` → menu painted after 196 ms; each next key echoed in 12–15 ms; while a reply streamed at 20 deltas/s, CPU was 0.02 s per 5 s without the menu and 0.55 s per 5 s with `@src` open (27×; at 100 deltas/s that is ~50 % of a core and 5–7 ms added to every event). In `~/code` the walk took 255 ms and each filter 5.4–6.7 ms over 20,000 paths.
  Impact: sluggish typing and frozen streaming whenever an `@path` is being typed in a large folder, idle or while steering.
  Verified: tested (`python3 scratchpad/C/tools/menucpu.py`; `BENCH_TREE=… cargo test … bench_mention_and_menu`).
  Suggested fix: compute the menu once per change of text, cursor or busy state (in `sync_menu`) and keep it in `App` for `live()` and the key handlers; lower-case the listing once when `mention::list` builds it; run the walk in `spawn_blocking` and show the menu when it lands (decision 40's "fresh per `@`" stays true).

- **[broker.rs:289-297]** The broker holds its server-map lock while a server starts (up to `INIT_TIMEOUT` = 60 s), so every other attach — to any server, from any session — waits.
  Scenario: `server()` takes `broker.servers.lock().await` and awaits `Server::start` (spawn + `initialize`) under it. A failed start isn't remembered, so the next attach to the same bad server holds the lock for another 60 s.
  Impact: one slow or wedged stdio server (an `npx` first run, a server that never answers) stalls every session's `mcp` calls and eager start-up (`Setup::new` awaits eager servers before the first paint, see next item); the client-side `attach` has no timeout of its own (intel-0b obs 10).
  Verified: tested (`bench_broker_lock_held_across_start` in the scratch crate): an unrelated fast server attached in 32 ms alone and in 2,760 ms while a server that answers `initialize` after 3 s was starting.
  Suggested fix: keep a per-launch slot (`HashMap<Launch, Arc<tokio::sync::Mutex<Option<Arc<Server>>>>>` or a `OnceCell`): take the map lock only to find/insert the slot, then start under the slot's own lock, so starts of the same server still serialize and different servers don't.

- **[setup.rs:64-75 → mcp.rs:187-206]** Eager MCP servers start one after another, inside `Setup::new`, before the first paint.
  Scenario: `start_eager` awaits `self.tools(name)` (connect, `initialize`, `tools/list`) for each name in a `for` loop; with the broker lock above, even separate sessions serialize.
  Impact: start-up time is the sum of the eager servers' start times rather than the slowest one's; one server that takes seconds (an `npx` download, an editor bridge waiting for its editor) delays the first paint by that much per server.
  Verified: traced.
  Suggested fix: `futures_util::future::join_all(names.iter().map(|n| self.tools(n)))` (`tools` takes `&self`), then insert the results in `names` order, so the tool list stays byte-identical and deterministic (cache rule); needs the broker fix to pay off through the broker.

### P3 - Low / Nits
- **[tui/mod.rs:2656-2665]** The streaming preview re-styles and re-wraps the whole unfinished line on every draw, so a long line costs quadratic CPU. 5,000 deltas: 0.13–0.14 s CPU with a newline every 12 deltas, 0.40 s as one 20 KB line, 4.8 s (5.5 s wall instead of ~1 s) as one 80 KB line, inline and fullscreen alike. Only model text goes through `Event::Text` (tool arguments don't), so it takes prose/code lines with no newline (minified JSON, base64, long tables). Verified: tested (`python3 scratchpad/C/tools/streamcpu.py`). Fix: preview only the tail that can show (the last ~6 rows × width, cut on a char boundary); the committed line is still styled whole when its newline arrives.
- **[llm/mod.rs:211-216; same pattern mcp.rs:486-500]** SSE parsing rescans the buffer from byte 0 for every chunk and shifts the buffer once per line. Measured on 4 MB in 16 KB chunks: one 4 MB line 208 ms vs 2 ms with a remembered scan offset; 2,000 lines arriving in one chunk 6.6 ms vs 0.14 ms; normal traffic (≤16 KB frames, short lines) 0.4 ms. Large single lines do occur with Responses' `response.output_item.done`/`response.completed`, which repeat a big `write` call's arguments (≈13 ms per 1 MB line, quadratic). Verified: tested (`bench_sse_lines`). Fix: keep a `scanned` offset across chunks and drain consumed lines once per chunk.
- **[tui/mod.rs:2513-2527, called :259 and :1009]** `refresh_branch` spawns `git rev-parse` and `git status --porcelain --untracked-files=no` synchronously after every main-loop iteration (each prompt, slash command, picker choice — not per key): 67–82 ms here (2k–20k files), delaying the turn's closing line and the redraw. Verified: tested (gitbench). Fix: run it with `tokio::process` and update the status line when it returns; read the branch from `.git/HEAD` without a process.
- **[main.rs:102 → session.rs:307-322; setup.rs:105; agent.rs:360; tui/mod.rs:1716; session.rs:150,154]** Extends [V4]. `killi -c` parses every log in the folder to pick the newest; then resume parses that log three more times (`Setup::resume` for the model choice, `Agent::resume`, `replay_log`), and `load` deep-clones every message (`entry["message"].clone()`, `as_array().cloned()`) instead of taking it. The user's largest folder (agent-hub: 58 logs, 22.8 MB, all parsed to list 47): `session::list` 35 ms, peak heap 2.7 MB (one log at a time, ≈2.5× the largest log); listing by mtime and parsing only the newest 20 user-lines gives identical results in 4.0 ms, and the newest 1 (for `-c`) in 0.4 ms. Scales at ≈1.5 ms/MB, so 200 logs × 5 MB ≈ 1.5 s on the runtime thread (extrapolated). Verified: tested (`bench_list`; the lazy variant's output compared equal). Fix: sort by mtime first, parse lazily, skip non-user lines, `take()` instead of `clone()`, and load the resumed log once.
- **[tui/history.rs:104-122; tui/mod.rs:1179-1180, 1435-1436, 2620-2627]** Fullscreen re-lays out the whole history for every `Resize` event: 39–54 ms at 20,000 entries (25k–40k rows), and a drag delivers many events, each processed with a full reflow and a full repaint. (At the 20,000-entry cap the history holds 6.9 MB of heap — bounded, but about half the advertised 15 MB.) Verified: tested (`bench_reflow`). Fix: coalesce — drain queued `Resize` events and reflow once per draw, or lay out lazily from the newest entry up to what the view shows.
- **[tui/editor.rs:242-285]** The prompt editor lays out its entire text on every draw, though at most `MAX_INPUT_ROWS` show: 0.11 ms per draw after a 10 KB paste, 1.1 ms after 100 KB, 10.9 ms after 1 MB (every key and, while busy, every delta/tick). Verified: tested (`bench_render_big_paste`). Fix: lay out only the lines around the cursor.
- **[llm/openai.rs:97-129, llm/anthropic.rs:149-251, llm/responses.rs:54-97; agent.rs:213-221]** Per-request conversion and side-request copies — intel-0a obs 21 items 1–2, confirmed but immaterial at today's sizes. `prepare` per request: 1.0–1.5 ms on the user's largest real log (1.2 MB), 3.8–6.2 ms at 4 MB, 7.7–10 ms at 12 MB (20 screenshots); the deep clone in `replay_history` is only 0.2–1.0 ms of that, serialization is the rest. Transient heap peaks at ~2.5× the body (31 MB for a 12 MB history); `side_request`'s `to_vec` (recap after every tool-using turn, `/btw`, peer asks) adds another history-sized copy (0.2–1 ms), ~3.5× in all. Verified: tested (`bench_prepare`). Fix if image-heavy sessions grow: serialize the stored messages through `Cow`/borrowed views (clone only messages carrying `reasoning_items` or a cache mark), and pass the side question as a suffix instead of copying the history.
- **[mcp.rs:427-434]** A request that times out (or is cancelled by Esc, or whose write fails) leaves its `oneshot::Sender` in `pending` until the server hangs up: ~100 bytes per occurrence. A late reply finds and drops it, so nothing misroutes. Verified: traced. Fix: a small guard that removes the id on drop.
- **[tools/files.rs:113-130; tui/paste.rs:38-60; tui/mod.rs:3574-3580]** Other blocking spawns on the runtime thread: `sips` shrinking a 2880×1800 screenshot 89–95 ms per `read` of an image (serial even across parallel reads and swarm subagents); `osascript` ≥41–45 ms just to start (the clipboard script does more); `pbcopy` + `wait` small. Verified: tested (timings) / traced. Fix: `tokio::process::Command` (or `spawn_blocking`) for `sips` and the clipboard script.
