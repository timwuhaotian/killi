### P1 - High
- **[session.rs:84-90; main.rs:102-105; tui/mod.rs:173-190, 2352-2368]** A second process can resume a log that a running session is still appending to. Nothing locks the log, and `-c`, `-r` and `/resume` all ignore the live registry.
  Scenario: session A works in folder X. In another terminal in X, the user runs `killi -c` (or `killi -p … -c`, or picks A's row in `/resume`, which lists every log in the folder without marking live ones). `-c` takes the log with the newest mtime, which is A's, because A is writing to it. h1 asserts `list(&cwd)[0] == A's log`. `Session::open` opens it with O_APPEND and no lock, so both processes now append. A's `assistant(tool_calls a1)`, then B's user prompt, then A's `tool a1` land in that order, and `load` returns `[system, user, assistant, user, tool]`.
  Impact: the log can never be resumed again. D21 promises an "exact, append-only log", but OpenAI and Anthropic reject a tool result that doesn't directly follow its call, so every request from this log fails, and nothing repairs it (see the torn-line P2). B's model also continues A's conversation, and both processes send the same session id as `prompt_cache_key`/`session_header`. Two facts make this likely: D49 counted 39 overlapping session pairs in one folder, and killi prints `killi -r <log>` after every session, which invites resumes.
  Verified: tested (`audit_h::h1_two_sessions_appending_to_one_log_interleave_and_break_tool_pairing`).
  Suggested fix: hold an exclusive `flock` on the log while a `Session` appends to it. The kernel releases it however the process ends, the same pattern live.rs uses for presence. `Session::open` tries the lock and refuses with "session <pid> is still running it (`killi sessions`)". `-c` skips held logs and the picker marks them. Leave the current session's own log out of the picker, or it would be refused with its own pid. Unlike `live::list()` (whose `Entry.log` field could also identify the holder), this works with `[agent] peers = false`.

- **[snapshot.rs:86-94, 108-113; tui/mod.rs:632, 1058-1060]** `/undo` is the safety net for running without approval prompts. One failed `git add -A` turns it off for the rest of the session without telling the user. A failed `/undo` throws its snapshot away, so retrying undoes two turns.
  Scenario A: at each turn start, `take()` runs `git add -A`. If any file vanishes between git's directory walk and its `stat`, the whole add fails. Background dev servers, test runs and editor safe-writes create and delete files in non-ignored folders. With a loop creating and deleting 50 files, 39 of 100 `add -A` runs failed with `fatal: unable to stat 'tmp/t44.json': No such file or directory`. An unreadable file fails the add every time (`error: unable to index file`). `take()` stores the error in `disabled` (:92) and never retries. Nothing is shown at that point; the reason appears only when the banner is redrawn (:1058). `undo()` checks `disabled` first (:109), so the snapshots taken before the failure are unreachable too (h8).
  Scenario B: `undo()` pops its target (:112) before running any git step. If `write_tree` (:113) then fails the same way, that snapshot is gone, and the user's retried `/undo` restores the one before it. Turn 1's work is wiped along with turn 2's (h14).
  Impact: users find out undo is gone only when they need it, or they lose an extra turn of work. D34 found most wall-clock time is spent waiting on jobs, often background tasks — exactly when files churn.
  Verified: tested (`audit_h::h8_one_failed_snapshot_turns_undo_off_for_the_rest_of_the_session`, `audit_h::h14_a_failed_undo_drops_its_snapshot_so_the_retry_goes_back_two_turns`; churn rate from `scripts/git_add_race.sh`). With up to 3 tries the failure rate fell to 6/100; `--ignore-errors` still failed 27/100 (`scripts/git_add_race2.sh`).
  Suggested fix: retry `add -A` a few times. If it keeps failing, skip only that turn's snapshot, say so at once in a notice, and keep earlier snapshots usable. In `undo`, read the last snapshot without removing it, and pop it only after the restore succeeds.

### P2 - Medium
- **[session.rs:356-379; tui/mod.rs:234-243, 2386-2396]** `/prune` deletes the logs and side folders of other sessions that are still running.
  Scenario: six sessions are running, and from one of them the user picks "keep the newest 5". `prune_in` sorts every log on the machine by mtime and spares only the caller's own (:362). An idle live session has an old mtime, so its log is removed together with its `<id>/` folder: the spilled full outputs the model was told to read, and the subagent logs. That session keeps appending without any error, into an unlinked inode. Its whole conversation vanishes when it exits, and its printed `killi -r` command fails.
  Impact: a running session's log is lost silently, and paths the model was given ("The full result is saved at …") no longer exist.
  Verified: tested (`audit_h::h3_prune_deletes_a_live_sessions_log_and_its_later_records_are_lost`).
  Suggested fix: skip logs another process holds (the flock from the first P1, or the paths in `live::list()`), and count only removable sessions in the picker.

- **[session.rs:84-90, 108-112, 130-134; agent.rs:224-235, 1339-1348]** A torn last line in a log destroys more than that one line.
  Scenario: a write stops part-way through a line. Two ways this happens: a crash or power loss mid-line, or a full disk, where `write_all` returns ENOSPC after a partial write. In the disk-full case, `push_meta` fails the turn. When the lost record was a tool result, `recover()?` (tui/mod.rs:645) then tries to write a placeholder result, fails too, and ends the TUI.
  (a) On resume, `open` appends straight after the partial bytes, so the first record written is glued onto the torn line and dropped by the next `load` (h2). That record is usually `recover()`'s placeholder result or the next prompt.
  (b) serde_json writes non-ASCII as raw UTF-8. If the cut lands inside a multi-byte character (`…`, `✓`, CJK text), `fs::read_to_string` (:131) fails the whole file: `killi -r` errors, `/resume` stops listing the session, and `killi -c` silently continues the previous session instead (h2b).
  (c) `load` skips any unparseable line silently (:134). A message skipped in mid-history leaves a tool call without a result. `unanswered` inspects only the last assistant message (h11), so `recover` never fills the gap and every request after the resume is rejected, with no hint why.
  Impact: after a full disk or a crash, the newest session either disappears or becomes unusable.
  Verified: tested (`audit_h::h2_a_partial_last_line_swallows_the_next_record`, `h2b_a_cut_inside_a_multibyte_character_…`, `h11_recover_only_answers_the_last_assistants_calls`).
  Suggested fix:
  - `open` truncates a tail that doesn't end in `\n`.
  - `record` remembers the file length and `set_len`s back to it on error.
  - `load` reads bytes, decodes per line (lossy or skip), counts skipped lines and reports them.
  - Resume repairs tool-call pairing across the whole history: placeholder results for any unanswered call, orphan results dropped. It says what it repaired.

- **[setup.rs:104-107; agent.rs:351-362; session.rs:130-164; main.rs:104; tui/mod.rs:272-273]** Resume ignores the logged `cwd` but keeps the logged system prompt, which names that folder.
  Scenario: at exit, killi prints `killi -r /…/sessions/-Users-me-code-app/123-456.jsonl`. The user pastes it into a new terminal window, which opens in `~`. The logged prompt still says "Working directory: /Users/me/code/app … Each bash call starts a fresh shell in the working directory" (prompt.rs:22-24). But `tools::Context.cwd`, the snapshots, the live entry, project MCP servers and skills all use `~`. Every `bash` call and every relative path now runs in another folder: `cargo test`, `git checkout -- .` or `rm -rf dist` hit the wrong place. Undo is off in `~` ("undo is off in your home folder").
  Impact: commands run in the wrong folder with no approval prompt, and `/undo` can't cover them.
  Verified: traced. `load` drops the `session` entry's `cwd`, and `Setup::resume` passes `self.cwd`, the current folder.
  Suggested fix: return `cwd` from `load`. In `main`, before `Setup::new`, change to the logged folder when it exists and differs, and say so; otherwise refuse and name the folder. Print `cd <dir> && killi -r <log>` at exit.

- **[snapshot.rs:113-119]** `/undo` rewrites every tracked file. Its four separate git steps can also interleave with another session's snapshot on the index both sessions share.
  Scenario: `read-tree <tree>` discards all stat info, so `checkout-index -a -f` writes every file in the snapshot. Undoing a one-file change in a 200-file tree gave the 199 unchanged files new mtimes (h7). cargo, make and tsc then rebuild everything, watchers reload, and editors re-read files. Separately, sessions in one tree share `<git_dir>/index`. If another session's `take()` runs its `add -A` between this undo's `read-tree` and its `ls-files`/`checkout-index`, it re-adds the current state. The undo then reports "2 files restored" and changes nothing (h9). This is unlikely, but silent.
  Impact: a full rebuild after every `/undo`, and occasionally an undo that silently does nothing.
  Verified: tested (h7). h9 is a simulated interleaving: undo's steps run one at a time with the other session's snapshot in between. The fix was also tested (`scripts/undo_alt.sh`): after `add -A`, a single `git read-tree -m -u <tree>` restored a modified file, a deleted file, a new file and a new folder, and touched 0 of 199 unchanged files.
  Suggested fix: replace `read-tree` + `ls-files --others` + `remove_file` + `checkout-index -a -f` with one `read-tree -m -u <tree>`: one command, one `index.lock`. Also give each session its own index (`GIT_INDEX_FILE=<git_dir>/index-<pid>`). That also removes the cross-session `index.lock` waits D49 handles with up to 3 s of `thread::sleep` on the runtime thread. Two caveats on the per-session index: each session's first `add -A` rehashes the whole tree once (there is no stat cache yet), and the `index-<pid>` files must be removed on exit or one accumulates per session. A side benefit: `read-tree -m -u` refuses to overwrite a file that changed after the `add -A` ("not uptodate"), where `checkout-index -f` overwrites it.

- **[config.rs:578-605, 742-762, 766-787, 793-830]** The line-based TOML editors misread legal TOML, and none of them re-parses its output before writing.
  Scenario: a table header is recognized only when the whole trimmed line is `[...]` (:587, :750, :774, :808).
  (a) `[providers.anthropic]  # work` is not seen as a header. So `killi logout opencode-go` (`remove_provider_key`) also deletes the next provider's `api_key`, and so does pasting a key (`set_provider_key`, used by the first-run guide and by re-signing in with `killi login`) (h4, h4b).
  (b) `/web-search-config` on a commented `[search]  # brave for now` header, or on dotted keys like `search.provider = …`, appends a second `[search]` table. The file no longer parses, and every later start fails with "invalid config" (h5, h5b).
  (c) A line starting with `[` inside a multi-line string, such as the `[prompt] system = '''…'''` block, is taken for a header. With no real `[search]` table, the new provider and key are written into the system prompt text, and search stays unset (h5c).
  Impact: API keys disappear silently, or the config can no longer be loaded. Only `with_models` validates its output (:736). The user's own config has none of these shapes today (counted: 0 commented headers, 0 dotted keys), so this is latent, but each shape is ordinary hand-written TOML.
  Verified: tested (`audit_h::h4_…`, `h4b_…`, `h5_…`, `h5b_…`, `h5c_…`).
  Suggested fix:
  - After editing, parse the output as `Config`, compare it with the parsed input (only the intended fields changed), and refuse to write otherwise.
  - Treat `[...]  # …` as a header, and skip lines inside `'''`/`"""` strings.
  - Write through a temporary file in the target's folder, fsync, then rename, as `Credentials::save` does (login/chatgpt.rs:78-86). Resolve a symlinked config first so the link survives.

### P3 - Low / Nits
- **[mcp.rs:129-152; later.rs:57-65; session.rs:185-187; config.rs:604, 649, 759, 786, 829]** Small shared files are read, modified and rewritten in place, with no lock and no temp-file rename. - **[setup.rs:106; agent.rs:362, 370]** Resume uses the current tool list, not the logged one (obs 10). Measured over this machine's 175 logs, the built-in tool list is identical from 0.4.12 to 0.4.19. Only 7 of 144 consecutive session pairs in one folder differ: the MCP gateway's description, or older versions. So a resume across an update rarely misses the cache, and the provider cache (minutes) has usually expired by then anyway. Using the logged list would offer eager MCP tools whose servers may not be running and would hide new tools, so keep the current list, but log a `tools` entry when it differs so `sessions.py` can attribute the miss. Separately, `accounted_messages = loaded.messages.len()` (:370) treats every message after the last `usage` record as already billed, which undercounts the first compaction estimate after a resume. `load` should remember the message count at the last `usage`. Verified: measured (`tools_by_version.py`, `tools_full.py`), traced.
- **[session.rs:56-58; snapshot.rs:35]** `project_dir` and the snapshot folder name both flatten `/` to `-`, so `/a/b-c` and `/a-b/c` collide (obs 22). The two folders share one session folder (so `/resume`, `-c` and `later.md` mix them) and one shadow git dir with a single index. Until the cwd P2 is fixed, resuming a listed log from the other folder runs it in the wrong tree. Verified: traced. Fix: append a short hash of the full path to both names, keeping the readable prefix.
- **[snapshot.rs:81, 124-127; tui/mod.rs:394-398, 526]** Some gaps in undo's coverage are reported as success:
  - Changes inside a nested repo or a git worktree under the tree are recorded as a gitlink and never restored, and undo says "Undone. No files had changed in the last turn." (h13).
  - The "another session worked since" warning comes from `live::list()`. A `-p` run or a session that worked in the tree and has since exited gets its changes undone without warning.
  - There is no per-file size cap. A changed 200 MB binary costs 4.9 s of `add -A` + `write-tree` on the runtime thread before the turn, and adds about 190 MB to `~/.killi/snapshots` per version, never collected (`undo_alt.sh`). Examples are `.blend` or scene files that the user's blender, godot and unity MCP servers edit.
  Verified: tested (h13), measured, traced. Fix: name the nested repos undo doesn't cover; exclude files over a size cap (for example 50 MB) through `info/exclude` and say which files those are.
- **[login/chatgpt.rs:157-163; llm/mod.rs:172, 195]** The ChatGPT token refresh runs inside the request future, which the TUI drops on Esc or `/exit`; SIGHUP also exits in the middle of an await. If the cancel lands after OpenAI rotated the refresh token but before `save`, the new token is lost. The next refresh then presents the old token, `refresh_token_reused` is in `UNUSABLE` (:47-48), and killi signs the user out, forcing a browser sign-in. Verified: traced. Fix: run refresh + save in a `tokio::spawn`ed task that the request awaits, so dropping the request doesn't cancel the refresh.
- **[mcp.rs:89-95]** A syntax error in `~/.killi/mcp.json` or the project's `.mcp.json`, such as a trailing comma, silently drops every server in that file: there is no `mcp` tool, `/mcp` is empty, and no notice appears. Verified: traced. Fix: add the parse error to `Setup` notes, so it shows in the banner's problems list.
- **[live.rs:146-158, 234-244; agent.rs:676-690]** `Registration::update` rewrites the presence file in place, then truncates it. If a reader catches the mixed bytes on both of `read_entry`'s attempts, that session drops out of the listing for one read. `peers_note` then appends two spurious reminders ("No other killi session…", then "Another … works…") to history and to the screen. This is rare. Verified: traced. Fix: pad the new JSON with spaces to the old length before `set_len`; whitespace keeps every intermediate state valid JSON.
- **[session.rs:63, 75-79; snapshot.rs:76]** Session logs are created 0644 inside 0755 folders, and snapshot repos 0755. The logs hold tool outputs and pasted secrets; the snapshot repos hold full copies of each tree. On this machine they are protected only because `~/.killi` is 0700, which killi sets only when it creates that folder itself (init, import, login). A hand-made `~/.killi` would expose them to other users in `staff`, since the home folder is 0750 with group `staff`. Verified: observed modes (`ls -l`). Fix: create logs 0600, and session and snapshot folders 0700.

### Checked and fine
- **ChatGPT credentials**: `chatgpt.json` is written to a temp file, `sync_all`ed and renamed, with mode 0600. The flock is double-checked: credentials are re-read after taking the lock. Login and logout also save under the lock. This is correct across processes: one refreshes, the others wait up to 30 s and use its result.
- **live.rs**: the stage → lock → rename protocol is sound. Stale detection with `try_lock_shared` is sound: the kernel releases the lock, so a reused pid can't pass for the old session. Files are close-on-exec. The peer uid is checked through `getpeereid`. Requests are capped at 16 KB. The socket folder is 0700. Timeouts are 300 s for ask and 10 s otherwise.
- **Broker exposure (obs 13)**: there is no uid check, but the socket lives in the per-user 0700 `$TMPDIR`. With `TMPDIR` unset, Rust 1.97.1's `temp_dir()` returns the per-user `/var/folders/…/T/` (via `confstr`), not `/tmp` (tested). So intel-0b's "/tmp, predictable name" premise doesn't hold for the toolchain that builds releases.
- **Two brokers started at once**: the connect → unlink → bind sequence has a window, but it never produced two live brokers in 170 simultaneous starts (`broker_race.sh`).
- **Broker id remapping**: each server has its own id counter, routes are keyed by broker id, and the client's id is restored on the reply. When a server exits, its routes are drained and its clients released, and they reconnect. A client that disconnects mid-request only leaks its route until the reply arrives.
- **Session record**: each record is one write per line (D35). Tool-call ids are rebuilt from the logged calls on resume, and `stamped` handles entries that aren't objects.
- **Undo modes and ignores**: undo restores exec bits and symlinks (h12). `.gitignore`d files are left alone (existing test). An undo that overwrites the user's hand edits made during the turn, or that reverts another live session's work after one warning, is the D24/D49 design.
- **update.rs**: the staging file sits beside the canonicalized exe, and the rename over the running binary is atomic, keeping running processes on the old inode. The fsync and timeout gaps belong to dimension J.
- **[V8]**: confirmed by reading (agent.rs:412 against session.rs:74-79). Fix seam: on resume, start `children` at the count of `agent-*.jsonl` files already in `session.dir`, or have `child()` take the next free name.
- **[V4]**: each resume also parses the chosen log up to four times (`list`, `Setup::resume`, `Agent::resume`, `replay_log`). Logs here are 125 KB median and 1.1 MB max, so this is minor next to V4's folder-wide parse.
- **obs 19's multi-line case for `set_provider_key`**: configs killi writes put `[prompt]` last, and `position()` takes the first matching header. So only a prompt containing a `[providers.<name>]` line followed by `api_key…` lines would be hit, which is negligible. h5c shows the `set_search` variant, which is the realistic one.
